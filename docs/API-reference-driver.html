TheRide — Driver API Reference

Base URL: http://localhost:3000/api/v1  ·  Auth: Authorization: Bearer <token>  ·  Content types: JSON and multipart/form-data  ·  Version: Nov 20, 2026

Driver journey order

Register → Verify email → Login → Onboarding-status (drives every screen)
→ Upload documents → Admin review → [Rejected? Re-upload] → Add vehicle
→ Admin approves vehicle → Inspection → Admin passes inspection → Dashboard
→ Create ride → Receive bookings → Run the ride → Get paid

GET /auth/onboarding-status — nextStep values for drivers:

nextStepMeaning
VERIFY_EMAILEnter the emailed code
UPLOAD_DOCUMENTSShow document upload screen
AWAIT_VERIFICATIONAdmin is reviewing — show "under review"
REUPLOAD_DOCUMENTSDocuments rejected — show upload screen again
ADD_VEHICLEApproved, but no APPROVED vehicle yet
DASHBOARDGo to dashboard
The old COMPLETE_PROFILE step no longer exists for drivers — that screen was removed from the design. License details come from the uploaded license image.

Password reset — mobile flow (code only, no web link)

POST /auth/forgot-password      { "email": "ugo@example.com" }
POST /auth/verify-reset-code    { "email": "ugo@example.com", "code": "1550" }
                                → { "data": { "resetToken": "9f2c…" } }
POST /auth/reset-password/9f2c… { "newPassword": "N3wPassw0rd!", "confirmPassword": "N3wPassw0rd!" }
  • The 4-digit code expires in 10 minutes; the code is consumed at the verify step.
  • The app holds resetToken in memory (valid 15 minutes) for the final call.
  • "Resend" = POST /auth/forgot-password again — fresh code, old token invalidated.

Inspection — required before creating a ride

POST   /inspections/:vehicleId   multipart/form-data
       files: frontPhoto, rearPhoto, dashboardPhoto,
              odometerPhoto, tyrePhoto, safetyEquipmentPhoto (all required)
GET    /inspections/:vehicleId
PATCH  /inspections/:vehicleId   (re-upload; resets status to PENDING)

Admin passes it with PATCH /admin/inspections/:id { "status": "PASSED" }. Photos are stored in Cloudinary (EcoRide/VehicleInspections).

Other vehicle endpoints

  • GET /vehicles · GET /vehicles/:id — list is ownership-scoped
  • PATCH /vehicles/:id — any body field optional, same photo fields optional

The first account saved becomes the default withdrawal target.

  • DELETE /bank-accounts/:id — remove an account

Withdraw

POST/wallets/withdraw

{ "amount": 500, "bankAccountId": "…" }   // bankAccountId optional — defaults to the default account
{
  "success": true,
  "message": "Withdrawal successful.",
  "data": {
    "amount": 500,
    "bank": { "bankName": "GTBank", "accountNumber": "0123456789", "accountName": "Ola Wale" },
    "balance": 700
  }
}
  • Debits the wallet immediately and records a WITHDRAWAL transaction ("Paid to {bank} ****last4") plus a "Withdrawal Successful" notification.
  • 400 "Minimum withdrawal is 100." · 400 "Insufficient wallet balance." · 400 "Add a bank account first."
  • Transfers are simulated for now — a real payout gateway slots in behind the same endpoint later.

Add Money (funding)

POST /payments/initialize   { "amount": 5000, "paymentMethod": "CARD", "paymentType": "WALLET_TOPUP" }

Returns a reference; the gateway callback (or, in testing, an admin's POST /payments/mock-callback/:reference) credits the wallet and records a TOP_UP transaction.

Ride lifecycle (driver actions)

EndpointEffect
PATCH /rides/:id/arriveMarks arrival; passenger gets "Driver Arrived" and acknowledges via their booking
PATCH /rides/:id/startStatus → ONGOING
PATCH /rides/:id/completeStatus → COMPLETED; each accepted passenger's wallet is debited the fare, the driver's wallet is credited the total, both notified
PATCH /rides/:id/cancelBody { "reason": "Passenger requested" } (free text, optional) — status → CANCELLED, cancelReason stored, all PENDING/ACCEPTED bookings cancelled and passengers notified
PATCH /rides/:id/locationLive location — { "latitude": 6.44, "longitude": 3.42 }
GET /rides/:id/locationPassenger polls driver's live location

Other ride endpoints

  • GET /rides/history/me — the driver's rides (dashboard list)
  • GET /rides/history — ride history
  • GET /rides/:id — detail (recomputes remaining seats for the requested travel date)
  • PATCH /rides/:id — edit trip (any create field optional)
  • DELETE /rides/:id
A stray or malformed ID on any /rides/:id route returns 400 "Invalid ride ID.".

11. Bookings

GET/bookings/driver DRIVER — Received Booking screen

Returns bookings across the driver's rides; filter client-side by bookingStatus for the Pending / Confirmed / Declined tabs. Any PENDING booking older than 15 minutes is auto-cancelled ("Expired — driver did not respond in time") and the passenger is notified — the design's "Expires in 03:54" countdown runs from createdAt.

Driver decisions

EndpointEffect
PATCH /bookings/:id/acceptPENDING → ACCEPTED; passenger notified "Booking Accepted"
PATCH /bookings/:id/rejectBody { "reason": "…" } — PENDING → REJECTED; passenger notified
Seats are held when the passenger books (remainingSeats drops). If a ride is cancelled, held seats are released. Wallet balances move at ride completion, not booking.
