TheRide — Passenger API Reference

Base URL: http://localhost:3000/api/v1  ·  Auth: Authorization: Bearer <token>  ·  Version: Nov 20, 2026

Journey order

Register → Verify email → Login → Onboarding-status (drives every screen)
→ Complete profile → Dashboard → Fund wallet → Find ride → Book → Ride

GET /auth/onboarding-status — nextStep values for passengers:

nextStepMeaning
VERIFY_EMAILEnter the emailed code
COMPLETE_PROFILEPOST /passengers/profile has not been called yet
DASHBOARDProfile completed — go to dashboard

1. Auth

Same endpoints as the driver flow. Differences only:

  • role is "PASSENGER"; phoneNumber is required; names optional.
  • No driverId — login with identifier (email or phone).
  • Password reset email contains the 4-digit code only (no web link): forgot-password → verify-reset-code (returns a resetToken) → POST /auth/reset-password/:resetToken with the new passwords.

5. Wallet, funding & bank accounts

  • GET /wallets → { "data": { "id": "…", "balance": 3800, "currency": "NGN" } }
  • GET /wallets/transactions — wallet movements (types: TOP_UP BOOKING_PAYMENT TRIP_EARNING WITHDRAWAL REFUND COMMISSION)

Fund wallet (required before booking)

POST /payments/initialize   { "amount": 5000, "paymentMethod": "CARD", "paymentType": "WALLET_TOPUP" }

Returns a reference; the gateway callback credits the wallet. (In testing, an admin triggers POST /payments/mock-callback/:reference.)

Bank accounts & withdraw

  • POST /bank-accounts { "bankName": "GTBank", "accountNumber": "0123456789", "accountName": "Ada Nwosu" } — 10-digit account number; the first account saved becomes the default
  • GET /bank-accounts · DELETE /bank-accounts/:id
  • POST /wallets/withdraw { "amount": 500 } — debits the wallet, records a WITHDRAWAL transaction, notifies; minimum ₦100; optional bankAccountId targets a specific account

POST/bookings — Join a ride

{
  "rideId": "32dd1049-…",
  "numberOfSeats": 1,
  "travelDate": "2026-11-21",              // required for one-time bookings
  "isRecurring": false,                    // optional; needs recurrenceDays/StartDate/EndDate
  "recurrenceDays": ["MON","WED"],         // only when isRecurring = true
  "recurrenceStartDate": "2026-11-23",
  "recurrenceEndDate": "2026-12-23"
}
{
  "success": true,
  "message": "Booking created successfully.",
  "data": {
    "id": "334256ec-…",
    "bookingReference": "ECR-1795200292709-190",
    "bookingStatus": "PENDING",
    "fare": "1200.00",
    "numberOfSeats": 1,
    "travelDate": "2026-11-21"
  }
}
  • The ride must be SCHEDULED with enough remaining seats; duplicate active bookings are rejected.
  • The wallet must hold at least the fare before booking — the fare is checked upfront and debited when the ride completes.
  • PENDING bookings expire automatically after 15 minutes if the driver doesn't respond — the "Expires in 03:54" countdown runs from createdAt. An expired booking is notified as "Ride Request Expired".

Booking status flow (passenger side)

EndpointNotes
GET /bookingsThe passenger's bookings — "My Rides" list; filter by bookingStatus (PENDING / ACCEPTED / REJECTED / CANCELLED / COMPLETED)
GET /bookings/historyHistory view
GET /bookings/:idDetail with ride, vehicle and driver info
PATCH /bookings/:id/acknowledgeConfirm the driver arrived — required before the trip can start
PATCH /bookings/:id/cancelBody { "reason": "…" } (optional) — held seats are released
After the driver completes the ride, the fare is debited from the wallet and both sides receive payment notifications.
